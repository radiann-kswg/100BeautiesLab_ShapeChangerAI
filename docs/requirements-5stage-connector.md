# 5 段階パイプラインとコネクタの要件（2026-11-18 合意）

ラジアンとの要件定義で決めたことと、保留にしたことの記録。実装の使い方は [src/README.md](../src/README.md)。

## 決めたこと

**パイプライン**

| 項目 | 決定 |
| --- | --- |
| Stage 1 | キャラクターデータと形状仕様から決定的にプロンプトを組む。LLM の推敲とランダムシーンは入れない |
| Stage 2 | 公式設定画を Vision で観察する。失敗時は続行／中止の回答を待ち、無回答は中止 |
| Stage 3 | Gemini でラフを生成。既定は単体 3 枚、合同は 1 体あたり 2 枚。Adobe の構図ガイドと SDXL は持ち込まない |
| Stage 4 | OpenAI の `GPT_MODEL` で検査。形状と違反の指摘が 3 件以上なら作り直し、それ未満はラフを起点に修正 |
| Stage 5 | 検査を通ったラフから完成画像を清書（既定 1 枚）。Canva 仕上げは連携があれば行い、省略できる |
| 単発生成 | `--quick` として残す。`--dry-run` は共通 |
| 自然文 | 複数に読める形状語は代表の形状に決め打ちし、選んだ形状を返答に明記する |
| 合同生成 | 2〜4 体。キャラクターごとに別の形状を指定できる |
| 改稿 | 以前の完成画像を起点に Stage 3〜5 をやり直す |

**コネクタ**（MCP サーバー `shapechange_mcp`）

- ShapeChangerAI 専用のサーバーにし、GeneratorsAI のコネクタとは分ける。
- ツール: 単体生成、合同生成、自然文からの依頼、改稿、ジョブ状況、確認待ちへの回答、実行一覧、実行ログ、形状一覧、キャラクター一覧。2026-11-19 に、GeneratorsAI のコネクタにそろえて、GCS に残った画像の一覧と取得、Canva のトークン更新を足した。
- Drive へは完成画像だけを、GeneratorsAI と同じフォルダーに `shapechange_` で始まる名前で置く。中間画像は `GCS_BUCKET` があれば GCS、無ければサーバー内。
- HTTP で公開する場合の認証は、GeneratorsAI と同じ OAuth。2026-11-21 から、接続のたびに合言葉（`MCP_AUTH_PASSPHRASE`）の確認画面を通す（それまでは自動承認）。利用者ごとの本人確認はしない。
- Canva は ShapeChangerAI 用の連携を別に作る（リフレッシュトークンを GeneratorsAI と取り合わないため）。
- 名前: VM での配置は `/opt/shapechanger`、Cloud Run のサービスは `shapechanger-ai`。

**VM での動かし方**（2026-11-18 決定。手順は [deploy-vm.md](deploy-vm.md)）

- GeneratorsAI の VM と同じ方針にする。既存の VM `generators-ai` に相乗りし、使うときだけ起動して、MCP クライアントから SSH 越しの stdio でつなぐ。公開ポート・Caddy・DNS・固定 IP は使わない。
- 当初の案（同じ VM に systemd と Caddy で常駐させ、サブドメインで公開する）は見送った。決めた時点で、GeneratorsAI の公開コネクタは Cloud Run へ移っており、VM は停止中で固定 IP も無かった。当初の案のために用意した systemd ユニットと Caddy の設定は、一度も動かさないまま 2026-11-18 に削除した。
- VM の操作は、ラジアンの PC の gcloud でエージェントが行う。
- コードは、VM に置いた読み取り専用のデプロイキーで GitHub から clone する。VM が使うブランチは `main`（PR #1 のマージ後に `develop` から切り替えた）。 2026-11-19 に、公開リポジトリを HTTPS で clone する形へ変えた（下の「公開リポジトリへの移管」）。
- `.env` の秘密の値は Secret Manager から VM が直接読む。PC の `.env` にある `DRIVE_*` は削除済みの OAuth クライアントの値で、使えない。

**公開コネクタ**（2026-11-18 決定。手順は [deploy-cloud-run.md](deploy-cloud-run.md)）

- claude.ai のコネクタとして使う公開の配置は、GeneratorsAI のコネクタと同じく Cloud Run にする。サービスは `shapechanger-ai`（`asia-northeast1`）で、インスタンス数・メモリー・タイムアウト・秘密の値の渡し方は `generators-ai` と同じ。
- 公開範囲も GeneratorsAI と同じにする（認証なしで呼べる Cloud Run と OAuth）。当初は自動承認の OAuth で、URL を公開の場に書かない運用に頼っていた。2026-11-21 に、接続時に合言葉を求める形へ変えた（GeneratorsAI の URL が公開のワークフローに書かれていたため。URL を知っているだけでは接続できない）。
- 配置は PC からスクリプト（`deploy/deploy_cloud_run.py`）で行う。送るのは、コミット済みのコード、キャラクターデータ、シェーダーの 2 ファイルだけ。

**進め方**

- 2026-11-18 に作業ブランチ `shape-pipeline` を `main` へマージした。以後は [Git ブランチ運用](../AGENTS.md#git-ブランチ運用) のとおり `develop` で進め、`main` へは Pull Request で反映する。
- エージェントは区切りごとにコミットする。push と Pull Request の作成は、ラジアンが依頼したときに行う。

## 画像入力・状態の指定・物品化（2026-11-20 合意）

ラジアンとの要件定義で決めたこと。GeneratorsAI のコネクタと共通の要件で、全文と DB の調査結果は非公開の作業メモにある（権利のやり取りの経緯を含むため、リポジトリには置かない）。ここには、このリポジトリに関わる決定と実装の状況を置く。使い方は [src/README.md](../src/README.md) の「入力画像」。

**実装の順番**（両リポジトリを通した番号）

| 順 | 内容 | 状況 |
| --- | --- | --- |
| 1 | このリポジトリの画像入力の土台（受け取り口、`images` の 4 役割、`quick`、`dry_run`、`run_meta.json` の GCS への保存） | 2026-11-20 に実装（作業ブランチ `feature/image-input`）。実際の GCS と生成 API では確かめていない |
| 2 | 両リポジトリの `state`（状態の指定）と、`Costume`・`Detachable` の読み取り | 2026-11-20 に両リポジトリとも実装 |
| 3 | GeneratorsAI の画像入力と、改稿の起点の読み取りの修正 | 2026-11-20 に実装（GeneratorsAI の `develop`） |
| 4 | このリポジトリの物品化（`object`・`face`） | 2026-11-20 に実装。実際の生成 API では確かめていない |

**入力画像**

| 項目 | 決定 |
| --- | --- |
| 役割 | `base`（加筆の起点）、`markup`（`base` に描き込んだ赤入れ）、`composition`（構図参考）、`reference`（生成画像と関係のない参考）、`object`（物品化の変形先の参考） |
| 渡すステージ | `base` は Stage 3 と 5、`markup` は Stage 3 と 4、`composition` は Stage 3 だけ、`reference` は Stage 3 と 5。それまで全ステージに渡していた `--ref` も、Stage 3 と 5 だけにした |
| 優先順位 | どの画像にも「キャラクターの外見は公式画像と設定資料が正しい」と添える。`reference` は `note` の用途にだけ使わせる。作風は文字で伝える。マスク（範囲指定の描き直し）は見送り |
| 構図参考 | 自動でグレースケールにして渡す |
| 赤入れ | 印は赤（線・丸・矢印・短い書き込み）。文字の指示（`revisions`）は任意で、あれば両方使う。`base` と縦横比が 2% 以上違う画像は受け付けない。Stage 4 は、印の場所が直ったかと、印や指示の文字が絵に残っていないかを `composition_issues` に数える |
| 受け渡し | コネクタの `shapechange_create_upload_slot` が、署名付き PUT URL（15 分有効）と `object_key` を返す。1 枚 10MB まで、PNG・JPEG・WebP。置き場は `<GCS の接頭辞>/uploads/<日付>/`、7 日で消す。base64・Drive のファイル ID・任意の URL は採らない |
| 受け付ける範囲 | 自分のバケットの自分の接頭辞にあるものだけ。出所（`provenance`）は毎回必須で、このパイプラインの生成結果（`own_generated`）とラジアン自身の作品（`own_work`・`own_photo`）だけ。許諾済みの第三者素材は見送り |
| 事前確認 | 生成のツールすべてに `dry_run` を足す。プロンプトと役割の付いた画像の一覧を返し、画像の生成は呼ばない |
| 軽い加筆 | 改稿の `quick` は、起点の画像の編集 1 回だけ。権利のゲートとプロンプトは残し、Stage 2 の観察・Stage 4 の検査・Canva を省く。完成画像 1 枚を、名前の末尾に `_iterN` を付けた新しい実行フォルダーへ保存する |
| 自然文 | `shapechange_generate_from_natural` は、画像入力の対象外 |
| スキルの手順 | 生成結果には `own_generated` を付ける。チャットに貼られた画像や PC の画像は、上げる前に 1 枚ずつ出所を依頼者に聞く。生成の前に `dry_run` の結果を見せ、承認を得てから本番を呼ぶ |

**物品化**（4 番。使い方は [src/README.md](../src/README.md) の「物品化」）

| 項目 | 決定 |
| --- | --- |
| 指定 | `mode` の代わりに `object`（変形先の物の名前）を渡す。どちらか一方。寸法を持たない別の種類の変形として扱う |
| 変形先 | 名前は必須。画像（入力画像の役割 `object`、1 枚）は任意で、Stage 3・4・5 に渡す |
| 残す手がかり | 配色と模様は物の表面に移す（必須）。顔は `face: keep \| none`（既定 `keep`）。耳と尾、腕と脚は、いまの `appendages`・`arms`・`legs` を使う。番号や紋章は物の表面に描く |
| 検査 | `shape_issues` は「名前と画像のとおりの物として読めるか、人の体の輪郭が残りすぎていないか」。`violations` は配色・模様と、顔の扱い。尾を残す指定なら本数を照合する。作り直しの線は 3 件のまま |
| 構図 | 1 枚絵（`layout=single`、変形量 1）だけ。途中経過と五方向図は、1 枚絵の結果を見てから決める |
| 変形先の画像の出所 | ラジアン自身の作品と生成結果に加えて、CC0・パブリックドメインの画像も受け付ける。出典の URL とライセンスの表記を `run_meta.json` に残す。形と素材感の参考としてだけ使い、ロゴ・文字・キャラクターの柄は写さないように指示する |

- 実装のときに決めたこと: 腕と脚の既定は `fold`、耳と尾の既定は `keep` にした（形状の変形はシェーダーの既定値を使うが、物品化にはシェーダーの値が無い）。合同（`--joint`）と `--size` には対応していない。体数の照合は物品化では行わない（顔の無い物は 0 体と数えられる）。尾の本数の照合は、`appendages` が `keep` のときだけ行う。変形先の参考画像からの写し込みは、`violations` の「写し込み: 〜」として挙げさせる。自然文の入口（`--natural`）は、形状番号だけを読み取る。

**状態と衣装**（このリポジトリでは「変形前の姿」の指定として使う）

| 項目 | 決定 |
| --- | --- |
| 状態 | DB に状態の名前があればその名前で選び、無ければ自由な文で体型と衣装・着用物だけを変える。DB が状態ごとに定めた変化（耳・尾・瞳）は正しいものとして通す。合同ではキャラクターごとに指定する |
| 着脱 | 自由な文で外せるのは、DB で `Detachable` の印が付いた品目だけ |
| 衣装 | `costume` に DB の `Costume` の値の名前を渡すと、その衣装を描く。名前に当たらない文は自由な衣装差分。指定が無ければ `usual`。61 の `idol` は選べない |
| 既定 | 豹変系女子は豹変前、獣爾騎兵は通常時（`normal`） |
| 検査 | Stage 4 に、指定で変えた体型と衣装を違反に数えないように伝える。尾の本数が無い状態では、本数の照合を省く |
| 一覧 | 選べる状態と衣装の名前を、`shapechange_list_characters` と `dry_run` の結果に出す |

- 実装のときに決めたこと: このリポジトリにも `costume` を足した（要件では GeneratorsAI の既存の引数を指していた）。合同の衣装の指定は入れていない。先行して入れた 61 の画像の固定指定は、上流で消えたあとも二重の備えとして残した。

**あわせて直したこと**

- 改稿の起点が、Cloud Run のインスタンスが止まると失われていた（`run_meta.json` をサーバー内からだけ読んでいた）。実行の `run_meta.json` を GCS の `<接頭辞>/runs/<run_id>/` に置き、手元に無ければそこから戻す。

**実装のときに決めたこと**（要件に書いていなかった点。2026-11-20、実装した側の判断）

- プロンプトの `[参照画像の扱い]` を、ステージごとに、実際に添付する画像の並びで組み直す。役割で渡すステージが変わるので、1 本のプロンプトを使い回すと、清書で「構図参考」と書かれた番号に公式画像が入る。
- 合同生成では、入力画像を全員を描く清書（Stage 5）でだけ使う。1 体ずつのラフは場面なしで描くので、全体の絵に対する起点・赤入れ・構図参考を当てられない。合同の赤入れは、反映されたかの検査をしない。合同の `quick` は、加筆の起点があるときだけ使える。
- `run_meta.json` と一緒に、完成画像も GCS の `runs/<run_id>/` に置く。完成画像は Drive にしか無く、記録だけ戻しても起点の絵が無い。消す期間は決めていない。
- `quick` の改稿が使い回すのは、起点の実行のプロンプトの文面ではなく、その実行が `run_meta.json` の `design_observations` に残した Stage 2 の観察。プロンプトの参照画像の一覧は、今回添付する画像で組み直す。
- Stage 4 で指摘が重く作り直すときは、Stage 3 と同じ画像を渡す（作り直しはラフの描き直しなので）。ラフを起点にした修正には、公式画像と赤入れだけを渡す。
- 自然文のツールにも `dry_run` を足した。画像は生成しないが、依頼文の読み取りに OpenAI の API を使う。
- `shapechange_list_runs` に、GCS だけに残っている実行を `location: gcs` として並べる。

## 構図と複数キャラクターの混在（2026-11-21 合意。手順 1 を実装、2・3 は未実装）

2026-11-20 の物品化（20 とバイナのシャチ型フロート）と、58 のカード平面化で分かったこと: 構図の文言が固定（物品化は「床に置く・接地影」、合同は「同じ床に重ならないように並べる」）で、場面の指定とぶつかる。「カードの山に混ざる」「水に浮かぶ」が描けない。合同は全員が形状変化する前提で、変形しない子を入れられず、物品化とも組み合わせられない。

ラジアンと決めたこと:

- 構図は `composition` で選ぶ。`showcase`（いまの見せ方。既定）と `scene`（場面に溶け込む）。自然文の入口は「混ざって」「浮かんで」「埋もれて」のような言い方から `scene` を読み取り、`dry_run` で見せてから確定する。五方向図と途中経過は `showcase` だけ。
- `scene` の寸法: その形の縦横比と厚みは守る。場面の物との大きさの関係は、場面の文で指定する（「トランプと同じ大きさ」など）。変形前の身長に対する実寸は問わない。
- `scene` の検査: 輪郭の 3 分の 1 くらいまでは、ほかの物に隠れてよい。選んだ手がかりは全部見えていること。
- 見分ける手がかり: 依頼ごとに「この子だと分かる手がかり」を選ぶ。決まった語（顔・配色・番号・耳・尾・髪のモチーフ・衣装の品目）から選び、自由文の補足を足せる。形ごとに既定を持つ。Stage 4 で、手がかりが見えているか、ほかの物へ移っていないかを確かめる。
- 合同の 1 枚に、変形しない子を入れられるようにする。キャラクターごとに「形状の番号／物品化／変形なし」を選ぶ。変形しない子は、最初は公式の既定の姿だけ。形態・状態・衣装の指定はあとで広げる。
- 変形しない子との関わり方（乗る・持つ・座るなど）は、場面の文に書くだけにする。検査では見ない。絵を見てから、選択式にするかを決める。
- 合同の物品化を入れる。キャラクターごとに違う物でよい。変形先の参考画像（`object`）は、キャラクターごとに 1 枚まで。
- 場面と追加の指定に書かれていない小物・家具・別のキャラクターは描かない（`showcase` でも `scene` でも）。
- 番号と紋章: 手がかりに選んだときだけ、読める位置に出す。選ばないときは設定の位置・大きさ・個数のまま扱い、設定で隠れている番号を無理に見せない。既定の手がかりに番号は入れない。58 の平面化で、設定では服の陰にある番号が、カードの隅や胸の中央に大きく描かれた。

作る順番: 1. 1 体の `scene` 構図 → 2. 合同の物品化 → 3. 変形しない子の混在。区切りごとに 1〜2 枚だけ生成して確かめる。

### 手順 1 で入れたもの（2026-11-21、1 体の `scene` 構図と手がかり）

- 引数は `--composition`・`--cues`・`--cue-note`（コネクタは `composition`・`cues`・`cue_note`）。使い方と語の一覧は [src/README.md](../src/README.md) の「構図と見分ける手がかり」。
- `scene` のプロンプト: 固定の「床に置く・接地影」を外し、場面の物との重なりと、輪郭の 3 分の 1 までの隠れを認める。寸法は比だけを渡す（cm を渡すと、場面の物との大きさの関係より実寸が優先されるため）。
- 手がかりは、プロンプトの `[見分ける手がかり]` と Stage 4 の検査に同じ一覧で渡す。検査は「手がかり: 〜」「番号: 〜」「取り違え: 〜」を挙げる。
- `scene` の尾の本数は、尾を手がかりに選んだときだけ照合する。体数は照合しない（周りのカードまで体数に数えられる）。
- 合同は、1 体ずつのラフに既定の手がかりを渡すところまで。合同での `scene` と手がかりの選び直しは、手順 2・3 で扱う。
- 生成での確認は、まだ行っていない（課金を伴う）。確かめる絵: 58 のカード平面化をトランプの山に混ぜる、バイナのシャチ型フロートをプールに浮かべる。
