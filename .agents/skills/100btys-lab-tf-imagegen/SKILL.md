# 形状変化絵（TF）の生成

リポジトリ `100BeautiesLab_ShapeChangerAI` の形状変化パイプラインを、依頼から完成画像まで進める手順。規則と仕様は次の正本にあり、このスキルは進め方を持つ。

| 知りたいこと | 正本（リポジトリのルートから） |
| --- | --- |
| 作業ルール、著作物の扱い、出力と記録 | `AGENTS.md` |
| オプション、出力の構成、コネクタのツール、環境変数 | `src/README.md` |
| 入力画像の役割（加筆の起点・赤入れ・構図参考・参考画像）、枚数、渡すステージ、受け渡し | `src/README.md` の「入力画像」と「コネクタ」 |
| 16 形状の番号と寸法 | `--list-modes`（コネクタは `shapechange_list_modes`）。実行のたびにシェーダーから読む |

## 入口

| すること | 入口 |
| --- | --- |
| 一覧と事前確認（課金なし） | CLI は、リポジトリのルートで `python -m src.pipeline.shape_pipeline …` に `--dry-run`。コネクタは、一覧ツールと、生成ツールの `dry_run: true`。どちらも明示的なバッジと形状番号なら API を呼ばない |
| 生成と改稿（課金あり） | コネクタ `shapechange_*` がつながっていればコネクタ。なければ `.env` に API キーを設定した環境の CLI |

自然文の入口（CLI の `--natural`、コネクタの `shapechange_generate_from_natural`）は、事前確認でも依頼文の読み取りに OpenAI の API を使う。対象の確認には、明示的なバッジと形状番号を使う。

リポジトリもコネクタも手元にないときは、明示的な `--badge` と `--mode` を使った `--dry-run` コマンドを依頼者に渡し、実行結果を受け取るまで生成に進まない。

## 手順

1. **対象を決める。** 依頼から、キャラクター（バッジ）、形状番号（0〜15）、レイアウト（`single`／`sequence`＝変形前→途中→完了／`five-view`＝五方向図）を読み取る。複数体を 1 枚に描く依頼は `--joint` で、キャラクターごとに形状を決める。
   - 形状語が複数の番号に読めるとき（「立方体」は 0 と 2、「球」は 4 と 5、「円柱」は 6 と 7、「平面」は 9〜12）は、形状の一覧を見せて依頼者に選んでもらう。
   - キャラクターは `--list-characters`（コネクタは `shapechange_list_characters`）に出るものから選ぶ。この一覧が AI 利用を許可されたキャラクターの全体。
   - 変形前の姿の状態や衣装の指定がある依頼（「豹変後の姿から」「巫女服で」「ブレザーを脱いだ姿で」）は、`state`／`costume` に渡す。事前確認に出る「選べる状態・選べる衣装」に名前があればその名前を、無ければ依頼の文をそのまま渡す。文での指定が変えるのは体型と着用物だけなので、耳・尾・髪・瞳を変える依頼は、設定のまま描くことを依頼者に伝える。

   完了: 対象が一覧にあり、形状番号とレイアウトが 1 つに決まっている。

2. **入力画像を決める（依頼に画像があるとき）。** 画像ごとに役割を 1 つ決める: 描き直しの起点は `base`、起点に赤で指示を描き込んだものは `markup`、ポーズや配置だけを借りるものは `composition`、それ以外の参考は `reference`（何の参考にするかを `note` に書く）。
   - 出所（`provenance`）を 1 枚ずつ確かめる。このパイプラインの生成結果は `own_generated`。チャットに貼られた画像と PC の画像は、依頼者に「自分の作品か、自分で撮った写真か」を聞き、答えのとおりに `own_work`／`own_photo` を付ける。依頼者以外の作品だと分かった画像は使わず、言葉での指定（`--style`、`--extra`）に置き換える提案をする。
   - 渡し方: CLI は `references/` か `outputs/` に置いた画像を `--images` で指定する。コネクタは `shapechange_create_upload_slot` で受け取り口を作り、返ってきた `upload_command` のとおりに上げて、`object_key` を `images` に入れる。

   完了: 画像ごとに、役割と、依頼者が答えた出所が決まっている。

3. **生成前に中身を見せる。** 決めた引数で事前確認（CLI は `--dry-run`、コネクタは生成ツールに `dry_run: true`）を実行し、プロンプト、参照画像と入力画像の一覧（役割と渡すステージ）を依頼者に示す。`[キャラクター（変形前の姿）]` から髪と瞳の色、耳、尾の本数、衣装を拾い、どれを残せば同じ子だと分かるか、どの部位が形に合わせて変わるかを具体的に添える。生成は課金を伴うので、枚数の見込み（事前確認の `max_generated_images`。5 段階の単体は最大 7 枚ほど、`quick` は 1 枚）も伝える。

   コネクタが `dry_run` を受け付けない（古い配置の）ときは、同じ指定の CLI の `--dry-run` コマンドを依頼者に渡し、その実行結果を受け取ってから示す。

   完了: 依頼者がその内容を見て、生成を承認した。

4. **生成する。** CLI は同じ引数から `--dry-run` を外して実行する。コネクタは `shapechange_generate_character`／`shapechange_generate_joint` でジョブを登録し、`shapechange_job_status` を完了まで確かめる。
   - Stage 2 の画像観察が失敗して確認待ち（コネクタは `awaiting_confirmation`）になったら、理由を依頼者に示し、続行か中止かの回答を待つ。回答を得てから、CLI は表示された確認に、コネクタは `shapechange_answer_reference_warning` に同じ回答を渡す。回答がないときは中止する。

   完了: 完成画像の場所（実行フォルダー名かリンク）を依頼者に渡した。

5. **結果を確かめる。** 完成画像を開いて原設定と見比べる。輪郭が指定の形状か、手順 3 で挙げた特徴が 1 つずつ残っているか、尾の本数が合っているかを見る。赤入れを渡した実行では、印の場所が直っているかと、赤い印が絵に残っていないかも見る。検査の指摘は `stage4_correct/analysis_log.json`（コネクタは `shapechange_get_run_logs`）にある。尾の本数の自動カウントは 1〜2 本ずれることがあるので、画像で数える。

   完了: 挙げた特徴の 1 つずつについて、残っているか崩れているかを依頼者に報告した。

6. **直す。** 崩れた点は改稿で直す（`--iterate-from <実行フォルダー名> --revisions "…"`、コネクタは `shapechange_iterate`）。`--revisions` には、変える点と保つ特徴（例: 「表情を笑顔にする; 尾は 7 本のまま」）を並べて書く。場所で伝えたほうが早い直しは、依頼者が完成画像に赤で描き込んだ画像を `markup` として渡す（手順 2）。表情や小物のような小さな直しは `quick`（起点の画像の編集 1 回、検査なし）、形や識別特徴に関わる直しは 5 段階で行う。改稿も手順 3 の事前確認と承認を経てから呼ぶ。改稿は新しい実行フォルダー（名前の末尾に `_iterN`）に保存される。変えた点と確認結果を、ローカルの実行ではそのフォルダーの `notes.md` に、コネクタの実行では依頼者への報告に残す。
